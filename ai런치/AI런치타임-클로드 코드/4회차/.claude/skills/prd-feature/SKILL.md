# PRD Feature

## 목적

짧은 기능 요청 한 줄만 보고 바로 구현에 들어가면, 나중에 "이게 아닌데"가 나올 확률이 높다. 요청이 짧고 모호할수록 그 안에 숨어 있는 가정(누가 쓰는지, 왜 필요한지, 어디까지가 범위인지)이 많다는 뜻이다. 이 스킬은 코드를 쓰기 전에 그 가정들을 사용자와 함께 명시적으로 확인하고, 합의된 내용을 PRD 문서로 남겨서 구현 단계에서 기준으로 삼을 수 있게 한다.

## 언제 질문 없이 바로 넘어가도 되는가

모든 요청에 다섯 가지 질문을 기계적으로 던질 필요는 없다. 요청 자체에 이미 목적, 대상, 범위가 충분히 드러나 있다면 그 부분은 묻지 말고 넘어가고, 빠진 부분만 확인한다. 사용자가 "질문 생략하고 네가 알아서 정리해" 같은 취지로 말하면 존중하고, 알고 있는 정보와 합리적인 가정으로 PRD 초안을 채운 뒤 "이렇게 가정했습니다"라고 밝힌다.

## 진행 방식: 대화형으로 하나씩

질문은 한 번에 몰아서 던지지 않고, 대화하듯 하나씩 순차적으로 묻는다. 앞선 답변에 따라 다음 질문이 달라질 수 있기 때문이다 (예: "누가 쓰나요?"에 "내부 관리자만"이라고 답하면 "비로그인 사용자 접근" 관련 질문은 건너뛴다). 다음 순서를 기본 흐름으로 삼되, 이미 답이 나온 항목은 다시 묻지 않는다.

1. **배경/목적** — 이 기능이 왜 필요한가요? 어떤 문제를 해결하려는 건가요?
2. **대상 사용자** — 누가 이 기능을 사용하나요? (예: 전체 사용자, 관리자, 특정 역할군)
3. **핵심 요구사항** — 구체적으로 어떤 동작을 해야 하나요? 가장 중요한 시나리오 1~2개를 예로 들어주실 수 있나요?
4. **범위 (포함/제외)** — 이번에 반드시 포함해야 할 것과, 이번엔 제외해도 되는 것은 무엇인가요?
5. **성공 기준** — 이 기능이 잘 작동한다는 걸 어떻게 판단하나요? (정량 지표든, "이런 경우가 없으면 성공"이든 괜찮음)

각 질문은 한국어로, 실제 대화체로 자연스럽게 묻는다. 사용자가 모호하게 답하면 구체적인 예시를 들어 한 번 더 좁혀서 물어봐도 좋다. 단, 답변을 얻기 위해 지나치게 캐묻지 말고, 2~3회 왕복 안에서 합리적인 수준으로 정리되면 다음 단계로 넘어간다.

## PRD 작성

질문이 끝나면 아래 템플릿으로 PRD 초안을 작성한다.

```markdown
# PRD: {기능명}

## 배경 및 목적
{왜 이 기능이 필요한지, 어떤 문제를 해결하는지}

## 대상 사용자
{누가 사용하는지}

## 요구사항
{핵심 동작을 항목별로 정리. 가능하면 사용자 시나리오 형태로}
- ...

## 범위
### 포함 (In Scope)
- ...

### 제외 (Out of Scope)
- ...

## 성공 지표
{완료 판단 기준}

## 확인이 필요한 가정
{질문에서 다루지 못했거나, 사용자가 답을 생략해서 임의로 가정한 부분이 있다면 여기에 명시}
```

"확인이 필요한 가정" 섹션은 실제로 가정한 내용이 있을 때만 포함하고, 없으면 생략한다.

## 저장

작성한 PRD는 `docs/prd/{기능-slug}.md` 경로에 파일로 저장한다. `{기능-slug}`는 기능명을 케밥 케이스(kebab-case)로 변환한 이름을 쓴다 (예: "검색 기능" → `search-feature`, "로그인 개선" → `login-improvement`). `docs/prd/` 디렉토리가 없으면 새로 만든다.

파일을 저장한 뒤에는 대화창에도 PRD 핵심 내용을 요약해서 보여주고, 사용자에게 확인을 받는다. 사용자가 수정 요청을 하면 파일을 갱신한다. 사용자가 승인하기 전까지는 실제 기능 구현(코드 작성)으로 넘어가지 않는다.
